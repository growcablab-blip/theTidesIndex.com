## 2. THE MIGRATION

`db/migrations/0029_publication_separate_from_review.sql`. Forward-only; no historical migration was
edited.

### Gates preserved, in full

Every provenance and completeness condition is unchanged:

- `tides_claim_provenance_ok` — an evidence link resolving to an exact location in a **citable**
  source (a source marked `replace` or `exclude` still cannot support a published claim)
- `interpretation_notes` present on every evidentiary claim
- `uncertainty_text` on high and critical importance claims
- `tides_protocol_provenance_ok`, plus `population_model`, an administration route, and
  `regulatory_context`
- `simple_summary` and `unknowns_summary` on compounds
- `what_it_proves` and `what_it_does_not_prove` on quality topics
- route records: exact location, citable source, population model
- regulatory statuses: an authority source, and a `checked_at` that is not in the future
- a **rejected** record is still refused

### Review coupling removed

- The `tides_has_approved_review(...)` conditions were removed from the six `tides_*_publish_gate`
  functions.
- `tides_enforce_state_coherence` no longer refuses publication for `unreviewed`, `captured` or
  `rejected` — only `rejected` remains blocked.
- **`last_reviewed_at` is no longer written by publication.** It moved to
  `tides_advance_review_state`, which sets it only when `performed_by = 'human'` and a
  `reviewer_user_id` is present, at the record's current version. A record nobody has reviewed now
  carries `null`, and the page renders that as "not recorded" rather than inventing a date.

### A second place the review date could have lied

Found while running the tests, and it is the one defect this separation could have introduced:

A material edit already bumped a record's version and dropped `review_state` back to `captured`,
because approvals are recorded against the words a reviewer actually read. It left
`last_reviewed_at` alone. Under the old policy that was harmless — the record failed its own gate a
moment later and was withdrawn, so no reader saw the stale date.

Publication no longer depends on those approvals, so an edited record now stays public, correctly,
since provenance is untouched. But it would have gone on printing **"last reviewed: <date>"** for a
version no person approved.

`tides_touch_and_version` now clears `last_reviewed_at` on a material edit, alongside the review
state it already reset. Nothing else about that function changed. The invariant now holds in both
directions: a review date exists only where a standing human approval at the current version exists.

### Kept deliberately

`tides_has_approved_review` itself is untouched, and still requires `performed_by = 'human'` with a
non-null `reviewer_user_id`. It has stopped being a publication gate and remains the definition of
an approved human review. The `reviews` table, `revisions`, `corrections`, `review_clocks`, the five
review types and role separation are all unchanged. No review history was deleted.

### Views

- `public_v_peptides` now carries `review_state`.
- `public_v_protocol_practitioner` and `public_v_protocol_simple` now carry `review_state` **and
  exclude demonstration protocols** via their parent compound (see §4).

## 3. THE DEMONSTRATION-DATA FIX

The baseline found that `protocols` has no `is_demonstration` column of its own, so the two public
protocol views filtered on publication state alone and the demonstration compound's protocols
(`DEMO-PR-A`, `DEMO-PR-B`) were reachable through both. Migration 0021 had excluded demonstration
records everywhere it could see them; it could not see these, because the flag lives on the parent.

Both views now exclude them with `NOT EXISTS (select 1 from peptides pe where pe.id = p.peptide_id
and pe.is_demonstration)` — `NOT EXISTS` rather than a join, so a combination protocol with no
`peptide_id` is not dropped from the register as a side effect.

`npm run db:strip-demo` then removed the fixtures themselves. It walks the foreign-key graph from
`information_schema` rather than using a hand-written list of child tables, because not every
reference to `peptides` cascades — `claims.peptide_id` is RESTRICT by design.

Removed: 1 demonstration compound, 1 quality topic, 2 sources, 4 staff profiles, and the
demonstration protocols that came with the compound.

**The database was rebuilt from scratch afterwards.** When the migration was amended (above), the
development database was deleted and recreated from migrations and the ordinary seed — and came up
with **no demonstration data at all** and `qa:production` clean *before* anything was published.
That is the check that matters for a deployment: the production seed path calls `seedDemoData` from
nowhere. It is reachable only from `npm run db:demo` and from one isolated integration test.

**One thing I could not attribute.** The baseline recorded 156 reviews by a demonstration reviewer.
By the time the cleanup ran the `reviews` table was already empty, and the script correctly reported
removing none. They were cleared somewhere between the baseline measurement and the cleanup —
most likely when the development database was restarted to apply the migration. I could not
establish which step did it, and I am not claiming my script removed them. What is verified is the
end state: **0 reviews, 0 profiles, 0 demonstration records.** The production seed path
(`npm run db:seed`) never creates demonstration data, so a fresh deployment database cannot contain
any.

## 7. JUDGEMENT CALLS — PLEASE READ

Three decisions were mine to make inside this section. Each is reversible, and each is flagged
because you may want the other answer.

### 7.1 Editorial syntheses were NOT published

Six `editorial_syntheses` remain unpublished, and `editorial_syntheses_publish_gate` was left
untouched.

**Reasoning.** Your instruction removes human review as a gate for *source-linked content*. A Tides
synthesis is not source-linked content — it is this index's own conclusion drawn across several
claims. Your decision of 21 September, that compound-specific and interpretive syntheses require an
approved human scientific review before publication, was about the index asserting its own
authority, which is a different question from making a sourced fact visible. It was also recent and
explicit, and the brief scoped the change to `tides_*_publish_gate` functions, which this is not.

**If you want them public**, it is a one-line change to that gate plus a re-run of the publish
script. Six records are affected.

### 7.2 A change request no longer blocks a *first* publication

This one needs stating precisely, because my first reading of it was too pessimistic.

**What still works.** `tides_withdraw_on_review` (migration 0005, untouched) withdraws a record from
the public site the moment a reviewer records `changes_requested` or `rejected` on it. A reviewer who
reads a live page and finds a problem still takes it down, and the record is flagged with their
comment. That protection is fully intact.

**What has gone.** Publication no longer consults an *existing* change request. Previously a record
carrying an open change request could not be published, because the gate wanted an approval at the
current version and a change request is not one. Now it can — until the reviewer records the request
again, which withdraws it.

So the narrow gap is: a record a reviewer has already flagged, and never revisits, can be published
over. **It has no effect on the current library**, which carries no reviews at all.

> **Closed in Section 3 (25 September 2026).** Migration `0030` makes an unresolved change request
> block publication, with parity tests at both layers. See
> `docs/V1_SECTION_3_WEBSITE_COMPLETION_REPORT.md` §1. The paragraphs above are left as they were
> written, because they record why the gap existed.

**My recommendation:** close it when convenient, not urgently. Given 0005 still catches the live
case, this is a smaller hole than I first thought. I did not implement it because it would add a
blocking condition you did not ask for, to a safety-critical gate.

### 7.3 Editing a published record no longer withdraws it

Before: editing a published record bumped its version, stranded the approvals, and the gate withdrew
the page. Now the edit bumps the version and resets `review_state` to `captured`, but the record
stays public.

This follows from the decoupling and I believe it is correct — the edit did not break provenance,
and the page now displays the honest, reduced review state with no review date. But it is a
behaviour change worth knowing about: **a post-publication edit is live immediately.**

### 7.4 A production-readiness blocker had to be re-aimed

`npm run qa:production` carried a blocker that counted **published records with no standing human
approval**, on the reasoning that "the publish gates are triggers and should make this impossible."
After publication it reported 485 — because that is now the ordinary, intended state.

Deleting the check would have removed a real guarantee, so I re-aimed it at the invariant that
matters under the new policy: **records carrying a review date that no approval supports**. A
published record nobody has reviewed is fine. A page saying "last reviewed" on a version no person
approved is not, and that is now what the gate refuses.

It currently reports zero, which is the same assertion the database makes: `last_reviewed_at` is
null on every peptide, claim, protocol and quality topic.
